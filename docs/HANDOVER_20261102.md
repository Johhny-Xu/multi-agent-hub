## 一、Qoder 国际版：真根因是「活动行没下发」被谎报成「今日已签」

### 1.1 实测坐实的根因

- 上游每日活动行是**开窗后延迟下发**的。同一账号：
  - 2026-11-01 **10:09**（开窗后 9 分钟）→ 拉不到行 → 旧代码判 `already` → **当天零重试**；
  - 2026-11-02 **00:57**（同一窗口）→ 拿到了 → 领到 **+100 Credits**。
- 旧代码判 `already` 的直接后果：`platformNeedsRetry` 只重试 `failed/pending`，
  `already` 不在其中 → 这一天再也不会拉第二次 → **每日 100 Credits 直接丢**。

### 1.2 设备指纹**不是**原因（实测排除，别再往这查）

同一 token、同一账号，三种身份请求 `GET /sash/api/v1/me/campaigns`：

| 身份 | 返回的活动行 |
|---|---|
| 完全不带设备头 | `[VIEW_DETAILS/CLAIMED]` |
| 本机 `runtime-info` 组件（env=0 / env=3 都试了） | **完全相同** |
| `~/.config/agenthub-qoder/device.env` 落盘三件套 | **完全相同** |

带不带 `?forceRefresh=true` 也**完全相同**（线上 n5095 实测，2026-11-02）。
Linux 上 `runtime-info` 在 env=0/3 下产出的是**同一份机器级**指纹。

真实活动行形状（国际版 2026-11-01 窗口）：
`campaignKey=act-20261101-825`、`actionType=CLAIM_BENEFIT`、
`benefit={"kind":"CREDITS","amount":100,"validity":30天}`、
`startAt=2026-11-01T02:00Z` → `endAt=2026-11-02T01:59Z`（= UTC+8 10:00 → 次日 09:59）、
`claimStatus=CLAIMED`。
另有常驻行 `act-20261020-944`（`VIEW_DETAILS`，首购加赠）——**不是**签到行。

### 1.4 更深一层的根因：重试调度把**还开着的领奖窗口**跳过去了

2026-11-02 02:10 在服务器上直接拉了三个国际版账号此刻的真实活动行，发现上一条修的还不够：

| 账号 | 本期（`act-20261101-825`）状态 |
|---|---|
| Kangsheng-Xu-745491318 | `CLAIMED`（11-02 00:57 领到 +100） |
| 花凄-johhny.xks | `CLAIMED`（11-02 00:57 领到 +100） |
| **Henry-Baker-henrybaker2689** | **上游至今没发这一期**（列表里只有常驻 `VIEW_DETAILS` 行） |

关键点：这一期的窗口是 **11-01 10:00 → 11-02 09:59**，而当时才 02:10 —— **Henry 的窗口还开着 7.8 小时**。
但旧逻辑给「没有活动行」的账号排的 `retryAt` 是**下一期开窗（10:00）**，**恰好落在他窗口关闭之后**：
这 7.8 小时里上游一旦补发活动行，我们再也看不到，那一期 100 Credits 永久作废。

服务端签到历史印证同一件事：11-01 10:09 判 `already` 之后，**到 11-02 00:57 整整 14.8 小时零重试**。

修法（`console/checkin.mjs`）：

- 新增 `qoderOpenWindow()` / `qoderPollAt()`：**窗口还开着就继续补拉** —— 开窗后 1 小时内每 10 分钟
  （参考实现 v1.0.12），之后每小时一次，一直补到**窗口关闭前 5 分钟**；只有进入窗口最后 5 分钟才等下一期开窗。
- 区分「本期已领」（等下一期开窗）与「本期行还没下发」（窗口内补拉）：
  不再用**自然日**比对窗口起始日 —— 00:00 一翻篇，还在窗口内的本期行会被算成「上一期」
  （实测 11-02 00:57 领到的行在 00:00 后就被算成上一期）。
- **重试预算按平台走**：Qoder 国际版/国内版 32 次（通用 8 次会在窗口中途耗光 →
  之后连下一期开窗都进不去；实测 `retryCount` 已用到 4/8）。老状态文件没有 `retryBudget` 字段时按平台名兜底。
- 平台级 `pendingReason` 改为**按优先级取**（缺设备身份 > 额度冷却 > 等上游下发 > 活动关闭 > 等开窗），
  卡片不再显示「待活动开启」而实际还在窗口内补拉。
- 前端 `awaiting_campaign` 徽章改为「等上游下发」，按钮保持可点（点了是真去拉一次，不是空转）。

测试：新增 `tests/console_qoder_window_poll.mjs`（14 项）。

## 二、两个国际版卡片「点了没反应」

### 2.1 前端根因

`client/qa-grid.js` 每个平台各写一份 `isSigned`，只认 `status === 'success' || 'already'`；
其余状态（`pending`/`failed`/`restricted`）一律渲染成**可点的「立即签到」**。
点击后只 `renderOverview(overview)` 重渲染同一份数据，状态没变 → 用户看到的就是「点了没用」。
账号级补签文案也只对 `settled` 平台生效，国际版处于 pending 时补签提示永远不出现。

### 2.2 服务端根因

平台级聚合把「有任一账号成功」当整体成功，**掩盖**了另一个账号的 pending；
`pending` 同时被「等开窗」「上游活动没开」「积分未确认」三种语义占用。

### 2.3 本轮实现

- **`pendingReason` 贯穿账号级 → 平台级 → 概览**：
  `awaiting_window` / `awaiting_campaign` / `identity_missing` / `quota_cooldown` /
  `campaign_closed` / `await_credits`。
- **统一聚合** `aggregatePlatformStatus()`：部分账号签成 → **`partial`**（不再粉饰成 success）。
- 概览新增 `signedAccounts`；`platformNeedsRetry` 把 `partial` 也纳入补签。
- **前端抽出独立模块 `client/checkin-card-state.js`**（浏览器 + Node 单测共用同一份），
  收敛掉 8 份复制粘贴的 `isSigned` + 徽章 + 按钮写法。
- **按钮语义**：等开窗 → 禁用「待开启 10:00」；额度冷却 → 禁用「冷却中」；
  缺设备身份 → 禁用并说明原因；上游活动未开启 → 可点「再试一次」。
- **点击有可见反馈**：点完在按钮上闪示本次结果（3 秒）并写明「在等什么」；
  一键全签后给出「全签完成 x/y · N 个待补」并列出仍在等的平台。

### 2.4 线上实测（2026-11-02）

```
codebuddy  status=pending  reason=campaign_closed    → 徽章「活动未开启」    按钮「再试一次」   可点
qoder      status=pending  reason=awaiting_window   → 徽章「待活动开启（10:00）」 按钮「待开启」  禁用
qoder-cn   status=success                           → 徽章「今日已领取」    按钮「今日已签」    禁用
```

### 2.5 顺带修：CodeBuddy 国际版「活动没开」会白耗当天重试预算

`campaign_closed` 时 `retryAt` 约到 **3 小时后**再探。以前 `retryAt=0` →
定时器当天空转，8 次/天的预算被耗光（线上实测已用到 6/8），活动中途开启反而没机会。
