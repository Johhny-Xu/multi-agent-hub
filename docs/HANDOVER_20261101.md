> 接 [`HANDOVER_20261028.md`](HANDOVER_20261028.md)。本轮只修一件事：
> **CodeBuddy 国际版（`codebuddy` 平台）的「自动活跃」打卡是假成功**——

## 一、现象与根因

- 现象：签到区「CodeBuddy 国际版」卡片两个账号都显示签到成功（credits「活跃+1」），
  但 `henrybaker2689@gmail.com` 的活跃**上游从未记上**；用户反馈「自动活跃并没有起作用」。
- 根因：`checkinCodeBuddyOne` 调 `~/.local/bin/codebuddy-intl` 包装器，
  而包装器按 `AC_intl_dir=$HOME/.codebuddy` **永远使用默认账号**（johhny.xks），
  并把它自己的 `auth.info` 覆盖进隔离 HOME 的共享存储。
  旧代码 `isIntlWrapper` 为真时直接跳过 `CODEBUDDY_CONFIG_DIR=dirname(acct.file)`
  ⇒ 所有账号都被默认账号「代打」。
- 关键事实（诱饵实测）：**CLI 的登录态在 XDG 共享存储**
  （`$HOME/.local/share/CodeBuddyExtension/Data/Public/auth/Tencent-Cloud.coding-copilot.info`），
  **不是** `CODEBUDDY_CONFIG_DIR/auth.info`。cfg 放 A 号、共享存储放 B 号 → CLI 认 B 号。
- 附带发现：`startAutoCheckinScheduler` 的平台清单手写了一份，**漏掉 `codebuddy`** ⇒
  国际版失败一次后当天再无重试机会（账号补签只管「从没签过的新账号」）。

## 二、改动

`console/checkin.mjs`：

1. 每账号独立沙箱 `~/.agenthub/checkin-sandbox/codebuddy/<uid>/`
   （独立 HOME + 独立配置目录），绕开包装器、直连 `~/.npm-global/bin/codebuddy`
   （`CODEBUDDY_REAL_BIN` 可覆盖）；models.json / settings.json 与线上国际版保持一致。
2. 打卡后从 CLI 日志读 `[AuthenticationSessionListener] [auth_success: <邮箱>]` 与 `"userId"`，
   与目标账号比对，**对不上就判失败**——不再报成功。
3. CLI 在沙箱里轮换过 refreshToken 时，把新 `auth` 块写回 hub 管理的凭据文件。
4. 沙箱 logs/traces 只留 2 天。
5. 平台清单统一为唯一事实来源 `CHECKIN_PLATFORMS`（= `Object.keys(PLATFORM_WORKERS)`），
   抽出纯函数 `platformNeedsRetry()` / `selectAutoCheckinPlatforms()`。

`tests/console_codebuddy_checkin.mjs`：+5 项（清单含国际版、重试口径、调度器选平台、
日志身份提取、账号比对防线）。

## 五、国际版「当日活跃」触发方式修正（2026-11-02，参考 L0NE-6/WorkBuddy-Daily）

用户给了参考仓库 [L0NE-6/WorkBuddy-Daily](https://github.com/L0NE-6/WorkBuddy-Daily)，
对照后确认**上一版的触发方式就错了**。

### 关键事实

- 参考实现 `workbuddy_intl_daily.py`（v3.9 起对齐上游 3.0.4–3.0.8）明确：
  国际版「每日活跃」**不是**调模型换积分，而是一组事件上报；
  `POST /v2/chat/completions` 只是**保活对话**，**只保活对话成功不算当日活跃**。
- 上游「当日活跃」计数**只认** `POST /console/as/conversations/`（网页会话）这一发
  （issue #277：桌面端对话与 `/v2/report` 都不进该计数）。
- 上游口径（v3.0.8）：**活跃上报或网页会话任一成功即算当日活跃完成**，积分由上游异步发放。

### 端点对照（实测两个域名指向同一后端）

| 用途 | 端点 | 实测 |
|---|---|---|
| 探测活动 | `POST /billing/meter/checkin-activity-status`（**无 /v2**） | ✅ 正确口径，返回 `active` / `today_checked_in` / `daily_credit=100` / `total_credits` |
| 探测活动（旧） | `POST /v2/billing/meter/checkin-status` | ⚠️ **废弃口径，恒返回 `active=false` 且积分全 0** |
| 官方领取 | `POST /v2/billing/meter/daily-checkin` | 活动关闭时 `code=10001` |
| 活跃上报 | `POST /v2/report`（`chat_request_send`，`userId` 必填） | ✅ HTTP 200 code=0 |
| 回读连登 | `GET /activity/growth/streak` | ✅ `days=2` |
| 网页会话 | `POST /console/as/conversations/` | ✅ 创建成功（会话 id 21169277） |
| 保活对话 | `POST /v2/chat/completions` | 仅维持「账号有调用」，**不计入活跃** |

### 改法（`console/checkin.mjs`）

- 新增 `fetchCodeBuddyActivityStatus()` / `buildCodeBuddyActivityEvent()` /
  `reportCodeBuddyActivity()` / `createCodeBuddyWebConversation()` /
  `keepaliveCodeBuddyChat()` / `isCodeBuddyAccountRestricted()`。
- 判定抽成纯函数 `decideCodeBuddyOutcome()`（可单测）：
  - 活跃上报与网页会话**都没**成功 → `failed`（明确写「调模型不算」）；
  - 任一成功 → 算当日活跃完成；**活动关闭 → `pending`，不白等 5 分钟**；
  - 活动开着 → 进平台层 5 分钟积分轮询，**积分到账才 success**；
  - 积分基线读不到 → `pending`（「未能确认到账」），不自称成功。
- 新增账号级风控 `11140 / request illegal` → `restricted`（`platformNeedsRetry` 不再重试）。
- **删掉**旧的 CLI 活跃路径（包装器/沙箱/日志身份核对/`runCodeBuddyCli`）——
  它正是「代打默认账号」假成功的根源；新链路全程用该账号自己的 Bearer token。
  凭据续期本就是 HTTP 实现，不受影响。

### 实测（n5095）

线上跑国际版签到，两个账号均：

```
pending | 签到活动未开启或已过期（活动未开启）；活跃链路已完成
（活跃上报成功（连登 2 天），网页会话已建），上游积分异步发放，待活动开启后重试
```

独立实验（336 秒轮询）：活跃上报 + 网页会话都成功，但连登仍 2 天、积分向量零变化
⇒ **上游签到活动当前关闭**（`active=false`、`claim_button_text` 空、`action_button.show=false`），
不发积分。历史 Bonus Pack 停在 10-21 / 10-30，与活动关闭吻合。

## 六、国际版成功判定改为「积分到账」（用户口径）

用户口径：**国际版活跃成功会发积分；5 分钟内积分没到账 = 活跃没成功**。

### 取证（n5095，真实账号）

1. **国际版有官方签到接口**，与国内版同款：
   - `POST https://www.codebuddy.ai/v2/billing/meter/checkin-status`
     → `active / today_checked_in / daily_credit / today_credit / total_credits / streak_days`
   - `POST https://www.codebuddy.ai/v2/billing/meter/daily-checkin`
2. **当前活动未开启**：两个账号 `active=false`；`daily-checkin` 返回
   `code=10001「签到活动未开启或已过期」`（国内版同接口回「今天已签到」→ 对照成立，
   说明不是账号问题，是活动本身没开）。
3. **「调模型发你好」不发积分**：模型调用成功（真实回复「你好！有什么可以帮你的吗？」，8.4s），
   随后 **338 秒**内 `get-user-resource` 的全部向量一个都没动：
   `TotalCount=19 / TotalDosage=710 / 存活包 19 / 包额度合计 610 / 包剩余合计 610 /
   包数 18 / 免费额度已用 0 / 免费额度剩余 100 / 最新包创建时间` 全部不变；
   `checkin-status` 的 `today_credit`/`total_credits` 恒为 0。
4. **Bonus Pack 时间序列**（只读探针翻两个账号全部 19 / 20 条额度包）：
   - `henrybaker2689`：最新一个包停在 **10-21**
   - `johhny.xks`：最新一个包停在 **10-30**
   - **10-31 与 11-01 两天，两个账号都没有任何新包**
   ⇒ 旧实现每天报的「签到成功（活跃+1）」在最近几天**从未真正发过积分**，假成功彻底坐实。

### 改法（`console/checkin.mjs`）

- 新增 `fetchCodeBuddyCredits()`（`POST /v2/billing/meter/get-user-resource`，取
  TotalCount / TotalDosage / 包额度 / creditsRemain）、`codeBuddyCreditsArrived()`
  （**只认正向变化**：新包 / 额度变大 / 总量上升 / 剩余变多——消耗不算到账）、
  `fetchCodeBuddyCheckinStatus()`、`claimCodeBuddyCheckin()`、`codeBuddyCampaignClosed()`。
- 判定链路：查 `checkin-status` →（`today_checked_in` 则 already）→ 官方 `daily-checkin` 领取
  → 再调模型保持活跃 → 取积分基线 → **并行轮询 5 分钟**（多账号共用一个窗口）
  → 到账 = success（显示 +N）；未到账 = failed。
- `CODEBUDDY_CREDIT_WAIT_MS = 5min`、`CODEBUDDY_CREDIT_POLL_MS = 15s`。
- **活动未开启（`active=false` 或接口回「未开启或已过期」）→ 记 `pending` 并写明原因，
  不白等 5 分钟**，等活动开启后由调度器重试。
- 读不到积分时如实标注「未做积分校验」，**不据此判失败**。
- 新增 pending 平台态（`console/checkin.mjs` + 前端展示）。

### 实测

线上跑一次国际版签到，**23 秒出结论**，两个账号均为：

```
pending | 签到活动未开启或已过期（官方签到返回「签到活动未开启或已过期」，
checkin-status active=false）；模型已调用但上游未发积分，待活动开启后重试
```
