## 2. 登录链路重构（8 项已知问题修复）

| # | 问题 | 根因与修复 |
| :--- | :--- | :--- |
| 1 | codebuddy 国际版无法自动获取账户 ID | 服务器上国际版 `auth.info` 是**半成品**（`accessToken` 为 `…/started?state=…` 跳转 URL，授权从未真正完成）。修复：URL 形态 token 一律判为未登录（`isLiveCredValid` 拒绝 http 开头 token）；ACP 授权回包后轮询等待真实凭据落盘（25s）；身份识别覆盖 `account`/`accounts[0]`/`allAccounts[0]` 三副本 + JWT payload + ACP 结果自带 userinfo 兜底 |
| 2 | codebuddy 登录踢掉网页端会话（CN 同理） | 官方 Keycloak 单会话策略，技术上无法避免。产品层防护：已登录时点登录弹窗会醒目提示"重新授权会使网页端/其他设备会话下线"，并引导使用不影响网页端的凭据导入通道 |
| 3 | mimo 自添加 API Key 被当成账号入库 | 粘贴 `sk-` Key 现在直接合并进线上 `auth.json` 立即生效、**不入账号库**；仅 API Key 的凭据（无小米 OAuth uid 且无其他通道）在 `_autoSyncLiveAccount` 层永不自动归档 |
| 4 | minimaxcode 不识别账户名 | 实证官方 mmx CLI 从不落盘账户名且无 userinfo API；但 `config.json` 的 `oauth.account` 是官方保留字段（`mmx auth status` 的 Account 行同源）。登录/导入时把用户在 WebUI 填的备注名注入该字段，账号列表/卡片头标/配额区同步展示 |
| 5 | trae 无法通过 OAuth 登录（链接有误） | 实证 Trae IDE `loginUrlBuilder`：授权链接**强制 PKCE**（`code_challenge` + `code_challenge_method=S256`，缺失即报错）；回调路径官方为 `/authorize`；登录主机改由 `GetLoginGuidance` 动态探测（国内/国际双区）；回调解析新增 `userJwt` 直通与 `authCodeInfo→AuthCode+CodeVerifier` 走 IDE 原生 `POST {host}/trae/api/v3/oauth/ExchangeToken` 兑换 |
| 6 | zcode 增加国际/国内切换 | 登录弹窗新增区域选择（🇨🇳 国内版 BigModel / 🌍 国际版 Z.ai），后端按区域向官方 init 接口传 `provider: bigmodel\|zai`，轮询响应字段（`pd.bigmodel`/`pd.zai`）与 `enc:v1:` 加密落盘双适配；生产实测两区均拿到正确官方授权链接 |
| 7 | "我已完成授权"是按钮逻辑而非状态检测 | 改为真实状态检测：调 `/api/auth/finish` 核验凭据落盘，未检测到明确报错并继续自动轮询，**杜绝假成功**；所有回调提交分支在归档失败时如实返回错误 |
| 8 | 多个登录按钮逻辑冲突 | 「🔐 OAuth 登录」与「+添加新账号」后端本就同走沙箱隔离流程，合并为单一「🔐 登录 / 添加账号」入口 |

## 3. CodeBuddy 登录链路深度修复与 XDG 共享存储实证

### 3.1 "反复写入卡死"事故链根因

用户粘贴 `/started?state=…` 完成页链接 → 旧代码把 **URL 字符串当作 accessToken 直接写入**沙箱 auth.info → 状态检测失败 → 误报成功并**杀死正在轮询的 CLI 进程** → 每次点击重复写入、永远无法完成。

### 3.2 官方协议实证（挖自 `@tencent-ai/codebuddy-code/dist/codebuddy-headless.js`）

```
POST {endpoint}/v2/plugin/auth/state?platform=CLI   → { data: { authUrl, state } }
GET  {endpoint}/v2/plugin/auth/token?state=<state>  → 轮询，pending 时返回 { code: 11217, msg: "login ing..." }
GET  {endpoint}/v2/plugin/account                   → Bearer 换账号信息（uid/nickname/phone）
```

- endpoint：国际版 `https://www.codebuddy.ai`、国内版 `https://copilot.tencent.com`，prefixPath 均为 `/plugin`；
- 真实 `auth.info` 结构：`{ account, accounts[], allAccounts[], auth: { accessToken, refreshToken, expiresIn, lastRefreshTime, expiresAt, refreshExpiresAt, … }, updatedAt }`；
- CN 版 JWT（RS256）：`sub`==uid、`preferred_username`==手机号、**email 恒为空**——CN 身份识别只能用 uid/uin/手机号，不能查邮箱。

### 3.3 关键坑：新版 CLI（≥2.164）会话不落 `auth.info`

实证：CLI 真实会话写到 **XDG 共享存储** `~/.local/share/CodeBuddyExtension/Data/Public/auth/<authentication.id>.info`（如 `Tencent-Cloud.coding-copilot.info`）——**只随 HOME，不随 `CODEBUDDY_CONFIG_DIR`**，且 CN/国际版共用同一文件。带日期戳的 `*.info` 是自动轮换备份。`CODEBUDDY_CREDENTIALS_IN_MEMORY=1` 时 CLI 只存内存不落盘。

Hub 修复方案：
- **ACP 回包成功后同时轮询 legacy 路径与共享存储**，发现共享存储凭据自动镜像为 legacy `auth.info` 归档（`findCodeBuddySharedAuth`）；
- **后台看门狗**：授权链接到达即提取 `state` 并行轮询官方 token 端点（走直连+代理兜底，约 8.5 分钟窗口）——CLI 自身 `loopGetToken` 在无代理网络下会卡死，由 Hub 直接完成落盘；
- 粘贴 `/started` 链接时提取 state 走官方兑换（短轮询），长等待交给看门狗；
- 注意：URL 里的 state 在 CLI 完成后仍长期返回 pending（11217），**CN 流不能依赖 state 轮询，共享存储扫描才是可靠检测**。

## 6. MiniMax 上下文档位选择器

实证 mmx CLI：上下文窗口由模型内置表决定（`MiniMax-M3.1-Flash-Preview`=524288、`MiniMax-M3`=1e6），`text chat` 无上下文参数；bundle 里唯一的 `m31ContextWindow`（512k/1m）仅用于 `mmx agent setup` 给**其他** agent 写配置。

## 8. 事故记录与红线

### 8.1 WorkBuddy 会话劫持事故（2026-10-13）

- **经过**：账号切换曾同步写入 CodeBuddy XDG 共享会话存储（本意让 CLI 跟随 hub 切换），但该文件**就是 WorkBuddy 桌面版的会话本体**——国际版登录完成后桌面版被顶成国际版账号。
- **处置**：共享存储已回写为 CN 会话（取桌面版当日轮换出的最新凭据）；肇事逻辑（`syncCodeBuddySharedAuth` 函数与调用点）**彻底删除**。
- **红线（写入 `accounts.mjs` 注释与本节）**：**hub 绝不写真实 HOME 的 CodeBuddy XDG 共享会话存储**。派发侧账号隔离本由 wrapper（`~/.local/bin/codebuddy-intl` / `codebuddy-cn`）的独立 HOME 机制承担——每次派发前把 legacy auth.info 拷入 `~/.codebuddy-intl-home` / `~/.codebuddy-cn-home` 的隔离共享存储再启动 CLI，互不踩踏也不碰桌面会话。hub 只允许在**沙箱内**读写共享存储（登录捕获）。
- **类似红线**：子代理调查凭据类文件时，只让脚本输出"键路径 + 类型"，绝不把原始值带进 AI 上下文。

### 8.2 BOM 字面量陷阱（编辑协作注意）

在 Git Bash 下编辑含 `/^\uFEFF/` 的正则时，直接粘贴**字面 BOM 字符**会被控制台编码污染导致替换失效；统一用转义形式 `\uFEFF`（或 `chr(0xFEFF)` 构造的脚本清扫）。

## 9. 运维 Runbook 更新（含 Hub 真实执行路径修正）

### 9.1 ⚠️ Hub 真实执行路径（交接文档修正项）

生产 `agent-hub.service` 实际执行的**不是**此前文档记录的 `/home/<user>/agent-hub/agent_hub.py`（那是停在 0.2.0 的旧副本）。以 systemd 单元最后一条 `ExecStart` 为准：

```
/home/<user>/.local/share/AgentHub-CodeArts/server/hub/agent_hub.py
```

部署 hub 代码须覆盖该路径后 `systemctl --user restart agent-hub.service`，并用 `curl 127.0.0.1:8765/health` 的 `version` 字段验证。

### 9.2 Console 部署流（不变，经验证）

```bash
scp console/{client/index.html,accounts.mjs,auth.mjs,server.mjs,vendor-quota.mjs} 分别到
  prod-node:/home/<user>/agent-hub-console/miniapp/client/ 和 miniapp/node/
ssh prod-node "cp miniapp/node/*.mjs /home/<user>/agent-hub-console/ && systemctl --user restart agent-hub-console.service"
```

验证：`curl 127.0.0.1:8890/api/accounts`、`/api/quota`、页面页脚版本号。

### 9.3 服务重启耗时（已根治 90s 超时）

- 此前有存活登录会话子进程或长连接时重启 console 会 SIGTERM 超时约 90s 后被 SIGKILL；现已在 `dispose()` 中接入 `authMod.cancelAllLogins()`、`closeAllConnections()` 及子进程 `SIGTERM -> 300ms SIGKILL` 回收，生产实测带活跃登录会话重启耗时 **0.063s（63ms）**。
