## 已修复的问题

1. **当前工作区未接入。** IDE 从当前项目的 `.codeartsdoer/mcp/mcp_settings.json` 加载 MCP。旧项目的配置不覆盖新项目；已给当前验收工作区登记连接，并把稳定插件从旧版更新到当前源码。安装报告新增版本、稳定目录、实际配置路径及后续步骤。省略工作区路径时明确提示未核实，CLI-only 安装不提示配置 IDE。
2. **原生工具调用方式不明确。** CodeArts IDE 的懒加载工具先经 `tool_search`、`tool_describe`，再用 `tool_call` 调用；显示出的 MCP 名称不能直接冒充已注册工具。九个子代理、Hooks 和调度技能已补充条件式指导，仍兼容直接注册 MCP 的宿主。
3. **未取得终态时过早结束。** 子代理在总等待预算内使用原 ref 查询；预算耗尽如实交回 running/unknown。宿主权限拒绝立即返回 blocked_permission，禁止重复请求、换工具名或交给父代理绕过；只有取得符合要求的非空 worker 答案才报告完成。
4. **Windows 官方 CLI 发现不完整。** 驱动与一键安装器识别 `installers/bin/codearts.exe`；直接运行 exe 时选择 CLI 专用配置和数据目录，避免误选 GUI AgentKernel。外部认证环境继续继承，适配器不添加关闭 TLS 校验的设置。
5. **信任错误诊断不清晰。** 官方“文件夹未被信任”归类为 `CODEARTS_PERMISSION_REQUIRED`，不输出私有目录或原始日志，不自动改变信任设置。
6. **Linux 取消时可能漏留后代。** 旧驱动会在 Hub 已拥有的组外再次创建进程组，外层取消只能清理驱动。隔离夹具复现并修复：Hub 设置内部归属标记，驱动同时核验自身为会话和进程组首进程，才让 CLI 留在外层组。独立运行仍拥有自己的组，正常退出也清理组内后代。测试覆盖外层 TERM/KILL、内层超时、父进程先退出、伪标记和无关进程保护；不据此追认历史超时残留进程的未知归属，也不宣称覆盖厂商主动另建会话的任意后代。
7. **Windows 状态查询误报停止。** 进程身份及命令查询分别在最多 10 秒预算内尝试两次。系统查询持续失败或现存进程的命令字段不可读时明确报错、保留进程记录；真正身份不符仍拒绝接管或停止。新服务启动后若无法确认身份，只清理已持有进程句柄的直接子进程。

## 明早在 IDE 验收

- 当前项目使用已登记的 MCP 配置；换项目时按 [原生包说明](../integrations/codearts/README.md#换工作区后连接-hub) 为实际工作区登记，复用已有外部连接文件。
- 重新加载 IDE 窗口，确认选用 DeepSeek v4.1 Flash 或其他可用的非盘古模型。
- 先调用 `/hub-status`。注册表心跳离线不等同于按需 CLI 不可调用；派发前看 `hub_capabilities`。
- 对现有 `mimocode-d5f1337f8a` 只查询原 ref，不重新派发。若 IDE 要求工具授权，由操作者决定是否允许；本轮没有修改权限或替操作者批准。
- 新测试可指定 `hub-codearts` 路由到已选定的远端 Linux Hub，模型选 `GLM-5.2`；不要用默认值暗中代替显式模型，也不要把本机目录当成 Linux 路径。

## 配置、备份与发布

凭据、认证环境、Hub 令牌和连接文件均保存在仓库外。Linux 只在现有 CodeArts 模型映射中新增经目录确认的 `GLM-5.2`，原默认值、其他 worker 和其余字段保留，变更前已备份。原生文件升级也保存了可回滚备份。

Windows 当前稳定插件目录为 `%LOCALAPPDATA%/AgentHub-CodeArts/plugin`，用户原生资产为 `~/.codeartsdoer`；客户端继续连接远端 Linux Hub，不要求本机启动 Hub。Linux 现有服务、历史任务和连接认证继续使用原部署。

最终冻结源码已同步 Linux 的 27 个明确文件，CodeArts 原生资产升级到 0.9.9，37 个受管文件校验通过。服务返回 0.9.9、24 个工具、9 个 worker，鉴权开启。升级前备份后再更新，任务验收后复核 6 个受保护配置和 355 个旧结果的哈希均未改变；唯一新增测试结果使总数变为 356。默认模型及认证没有在部署中改动。

验证范围与源码摘要见本页配套的 `codearts-ide-followup.json`。模拟回归、真实宿主调用、真实模型任务及权限受阻分别记录，不互相替代。

## 首次完整回归与追加排查

初轮跟进源码的 Linux 完整回归为 29/29 组通过；Windows 为 31/32 组通过，唯一失败是仅升级插件后，状态检查返回停止，与预期运行不符。安装配置和进程记录没有被升级动作改写。独立重跑该用例通过，但不足以解释首次失败，其具体触发原因仍未确定。

随后对健康的隔离 Hub 注入一次 Windows CIM 查询超时，稳定复现了另一项已确认缺陷：旧实现将查询失败当成进程不匹配，可能显示停止，并在停止操作中丢失进程记录。修复后短暂查询故障有界重试；持续失败明确报错、保留记录，不把未知状态当成已停止，也不放宽进程身份核验。该故障注入证据与首次偶发失败分别记录。

最终源码于 2026-10-10 完整复测：Windows **32/32 组**、Linux **29/29 组**通过，测试过程中源码未变。两端均使用已安装的 `google-antigravity==0.1.21`，真实 SDK 协议测试各 5 项通过；这不等于 SDK 已做模型推理。Windows 打包/服务组 26 项通过，包含超时、不可读命令字段、身份不符及失败启动清理回归。最终报告与初始失败报告分别保存，冻结归档及报告 SHA-256 写入配套 JSON。
